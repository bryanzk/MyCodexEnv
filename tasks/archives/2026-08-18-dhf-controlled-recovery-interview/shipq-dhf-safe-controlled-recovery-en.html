The strongest recovery evidence begins after a write already changed the remote document.

A Google Docs canary write produced a side effect, then failed its structure assertion. The problem was no longer “did the API run?” It was how to return a mutated, untrusted remote state to a proven state without widening the damage.

Selected case: partial write → fail closed → native rollback → independent readback → new manifest → fresh authorization → controlled completion.

Observed recovery sequence

01 · Lock

Manifest bound source, document, section, revision, and digest.

02 · Canary

Content changed, but structure readback failed.

03 · Stop

Remaining documents froze; the mismatch receipt remained permanent.

04 · Restore

The owner used native version history; the agent read back content and styles.

05 · Reauthorize

Writer fixes produced a new HEAD, manifest, digest, and confirmation.

06 · Complete

Three documents and four H1 sections succeeded; two no-change documents were not written.

SAFE controls in the case

SSpecification

Five allowlisted documents, changed sections only, explicit structure and style DoD.

AAuthorization

Live scoped confirmation bound to digest and revision; retry required new authority.

FFacts

Source commit, pre/post revisions, receipt v3, and staged fresh readback.

EError-recovery

Mismatch classification, no blind retry, native restore, independent verification, and handoff.

State constraints

MISMATCH ─X→ RETRY

An error is evidence to stop, not authority to repeat a side effect.

RESTORED ─X→ EXECUTE

Restoration closes the old incident; it does not grant a new write.

OLD DIGEST ─X→ WRITE

A changed HEAD, manifest, digest, or revision invalidates old confirmation.

SUCCEEDED → FULL READBACK

API success alone is insufficient; the terminal state requires readback and a final record.

Evidence boundary: this historical case does not prove current connector authority or authorize a new remote write. Current target revision, scope, and permission must be checked again.
