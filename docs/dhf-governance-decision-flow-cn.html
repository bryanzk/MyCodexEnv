Delivery Harness Framework / DHF 治理判定流程

工具真正跑起来之前发生了什么。

生命周期流程图和 Skill 路由图回答的是一个任务走哪条路线。这张图回答的是另一个问题：对任意一次工具调用，什么条件成立它才被放行，不成立又会怎样。拒绝边和验证失败回边都画了出来，因为只有成功路径的 agent 就是个 demo。

治理判定流程

每一次工具调用都要过这道门。

把它当成强制路径读，不是当工作流读。守卫跑在 PreToolUse，所以拒绝发生在副作用之前，不是之后。图里的门分两种：由 hook 强制执行的，和目前还只是文字规则的。只靠文字规则的门，图上直接标明。

怎么读这张图

这张图在主张的四件事。

1. 三类目标在任何档位都被拒存放凭据的文件；注册和实现 harness 自身的文件与目录；系统持久化位置，例如 shell 启动文件和开机项。任何阶段、任何声明都打不开它们。
2. 更严的档位由 owner 决定owner 按工作区设定档位。默认档只有上面三类拒绝。governed 档下，写和删还需要一个由 owner 声明的阶段，并且目标必须在工作区根目录之内。
3. 守卫出错时拦住写入守卫自己抛出错误时，写和删被拦，其余调用放行。2026-08-18 到 2026-11-26 期间，守卫每次调用都出错，宿主把崩溃当成了放行。这条规则就是为此加的。
4. 每次阻断都留记录，每条主张都有探测阻断会追加一条带原因代码的证据，每次调用都会更新守卫回执。由 hook 强制的每个方框都有一条不产生副作用的探测，结果在状态页的一致性表里。
边界

这张图没有主张的事。

这是在一台机器上实际运行的强制路径：维护者的 Mac Studio，Codex CLI 0.172.0，探测日期 2026-11-27。其他宿主以架构状态页为准。有四处限制，图上没有藏。守卫只判断结构化的文件调用，藏在 shell 命令里的写入不解析。执行 lane 和验证这两步是文字规则，不是 hook。agent 可以在自己的 shell 里运行声明命令，所以声明的阶段只留审计痕迹，不是硬边界。Plan Governor 保持 shadow，production_status = no_go。
