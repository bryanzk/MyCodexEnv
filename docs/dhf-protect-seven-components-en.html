DHF Runtime Promotion / Seven Protected Targets

PROTECT: Seven Protected DHF Runtime Components

These are not seven WALs. One fsync-backed WAL transaction promotes seven cooperating runtime components together. If any target fails, the whole promotion is restored in reverse order.

1 WAL transaction → 7 protected targets → 1 verified runtime state

Position, restrict, observe, and thread the work; empower the owner, contain impact, and transact the release.

Seven components / WHY · WHAT · HOW

Each component closes a different control gap

P

Position

Know where the task is
WHY
Without a reliable stage, the system cannot distinguish valid progress from an unauthorized jump.
WHAT
Resolve task phase, durable state, and recovery facts.
HOW
Read the phase the owner declared for this workspace. Without a declaration there is no phase, and the governed profile then refuses writes.
On Codex: codex/hooks/task_state.py
R

Restrict

Stop actions that should not happen
WHY
Prompt guidance can advise an agent, but cannot enforce a business boundary.
WHAT
Allow or block a structured file call before it runs. Shell commands are not parsed.
HOW
Refuse credential, control-plane, and OS-persistence targets in every profile. In the governed profile also require a declared phase and a target inside the workspace. A Guard that fails blocks writes.
Core: dhf/core/guard_core.py · On Codex: codex/hooks/harness_guard.py · On Claude Code: .claude/hooks/dhf_guard.py
O

Observe

Make outcomes independently checkable
WHY
Without post-execution facts, “done” is only an agent's assertion.
WHAT
Capture real outcomes as recoverable, auditable evidence.
HOW
After a tool call, append a record of what ran. A block appends its own record with the reason code. Observation never grants permission.
On Codex: codex/hooks/harness_observer.py
T

Thread

Keep work continuous across sessions
WHY
Session loss or compaction can erase business context and trigger duplicate work.
WHAT
Restore task bearing, boundaries, and the next safe action.
HOW
At session start, read the State Log and Git and give the new session four facts: phase, next safe task, boundary verdict, and dirty status. A bearing that does not arrive is recorded as a miss.
On Codex: codex/hooks/session_bearing.py
E

Empower

Give the accountable owner an explicit control
WHY
Implicit authority is hard to audit and easy for stale sessions to reuse.
WHAT
Declare, inspect, and revoke time-bounded phase capability.
HOW
The owner sets a profile and declares a phase from the command line; each has a time limit and an audit line. An agent can run the same command from its shell, so this control leaves an audit trail and is not a hard boundary.
On Codex: codex/bin/codex-task
C

Contain

Limit the blast radius
WHY
A reasonable action in the wrong directory can still create an incident.
WHAT
Declare governed roots, protected roots, and allowed scope.
HOW
In the governed profile a write must land inside the workspace root, the temp directories, or roots the owner listed. The harness installation stays protected in every profile.
On Codex: codex/runtime/harness-scope.json
T

Transact

Promote all seven together or restore all seven
WHY
A partial update creates a mixed runtime with incompatible control components.
WHAT
Fix the seven-target set and journal intent, application, and final commit.
HOW
Atomically replace and fsync each target; restore in reverse on failure. Only the owner runs it, after approving the source digest.
On Codex: codex/runtime/harness-guard-targets.json + scripts/sync_codex_home.sh

How the seven protect one business action

1 · ThreadRestore session bearing
2 · PositionResolve the phase
3 · ContainLoad governed scope
4 · RestrictGate before execution

Empower is the accountable owner's authorization control. Transact is the outer release envelope that safely installs the entire control plane.

One WAL / Atomic promotion

The WAL protects runtime consistency, not file copying

Back up seven targets
Write PREPARED
Journal each INTENT
Atomic replace + APPLIED
Verify manifest and policy
COMMITTED or ABORTED

harness/deployed-manifest.json is also captured for rollback, but it is a deployment receipt—not one of the seven formal promotion targets.

Evidence boundary

The seven functions are the contract; each host implements them separately

A function is verified on a host when a side-effect-free probe passed there and its receipt is in docs/dhf-conformance.json. The table is the state on 2026-11-27. The Codex column is Codex CLI 0.155.1 on one machine; a new host version makes its receipts stale until the probes are run again. The 24/24 parity and 18/18 isolated host probes from 2026-08-10 described a Guard that was later simplified. They are history, not current evidence.
