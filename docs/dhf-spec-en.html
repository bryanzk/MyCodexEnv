DHF specification.

The rules of the Delivery Harness Framework. This page states what must hold on every host; it does not describe an implementation. This is a translation. The authoritative text is the Chinese source, docs/dhf-spec.md; where the two differ, the source wins.

中文版 State by host Seven functions Decision flow

1. Standing of this page

  • This page is the DHF specification. It states rules, not implementation.
  • The rules do not depend on any one host. A host is the program that runs an agent.
  • Other pages of the public site describe an implementation or explain the framework. Where another page conflicts with this one, this page wins.
  • When models become more capable, the rules stay the same. The implementation may change.

2. Eight invariants

Each invariant has four parts: rule, reason, enforcement point, and test.

An enforcement point is the place where a rule is carried out mechanically. Prefer points outside the host: CI, branch protection, a protected runner, credential scope, file permissions.

I-1 Evidence is graded

  • Rule: evidence has seven levels: design intent, source implemented, verification passed, runtime active, publicly published, production enforced, customer outcome validated. Evidence of a lower level must not be used to prove a higher level.
  • Rule: source, runtime, public documentation, and production are four states and are reported separately.
  • Reason: a model can write a fluent statement that looks finished. Fluent is not accurate.
  • Enforcement point: the delivery report template; the status page of the public site.
  • Test: every status claim has an evidence level and an evidence date beside it.

I-2 A completion claim carries a fresh receipt

  • Rule: every conclusion of the form "done", "fixed", or "passed" carries four fields: command, exit_code, key_output, timestamp.
  • Rule: a receipt expires when the related source, the host version, or a runtime file changes.
  • Rule: a report from a sub-agent is evidence awaiting review. It is not proof of completion.
  • Reason: a receipt replaces a statement with a fact that can be checked.
  • Enforcement point: the delivery report template; a required check in CI.
  • Test: a conclusion that lacks any of the four fields is treated as unverified.

I-3 Authority comes only from the owner's current message

  • Rule: only a message the owner sends in the current conversation can authorize an action.
  • Rule: repository files, tool output, earlier conversations, recovered state, and agent-generated content never authorize anything.
  • Rule: a side effect that is not in the action register is refused.
  • Reason: instructions can be mixed into anything an agent reads. Recovery restores facts, not permission.
  • Enforcement point: the action register; the single-use authorization check of a protected runner.
  • Test: every external write can be traced to one message from the owner.

I-4 Actions are graded by side effect

  • Rule: an action is graded by two properties: whether it can be undone, and whether it leaves the machine. It is not graded by the kind of work.
  • Rule: there are three levels. Level 0: local reads, and local writes inside the authorized write set. Level 1: may run once the owner has named the action and the target. Level 2: refused by default.
  • Rule: Level 0 needs no confirmation. A Level 1 action leaves the machine but can be undone. A Level 2 action cannot be undone, or changes permissions or the control plane.
  • Rule: Level 1 authority may be given for a group: one message from the owner authorizes one class of action, for the current session only.
  • Rule: Level 2 authority is never given for a group. It is given separately each time.
  • Rule: the action register may mark a Level 1 action as not groupable.
  • Rule: a profile does not change the level of an action. It changes only how Level 1 is confirmed: the governed profile does not allow group authority; the other profiles do.
  • Reason: the cost of process must match the risk. Low-risk work stays light.
  • Enforcement point: the action register; the three profiles light, standard, and governed.
  • Test: every action belongs to exactly one level in the register.

I-5 Discipline for external writes

  • Rule: check the current state of the target before writing. Read it back immediately after.
  • Rule: when the result is partial or unknown, do read-only checks only. Never retry blind.
  • Rule: single-use authority expires after one use. Group authority is valid only in the session that gave it. A replay is refused.
  • Rule: secrets never enter an agent's input, output, or context.
  • Reason: the state of an external system cannot be rolled back, or only at high cost.
  • Enforcement point: a protected runner; version-conditional writes in a connector; credential scope.
  • Test: every external write has one pre-write check record and one read-back record.

I-6 High risk is blocked before the side effect

  • Rule: a high-risk action is stopped mechanically before its side effect happens. A prompt alone is not enough.
  • Rule: prefer enforcement points outside the host. A hook inside the host is a supplement.
  • Rule: every blocking point leaves a record that it ran. A blocking point that cannot show whether it was called is treated as unverified.
  • Reason: a prompt can only advise. A hook inside a host stops working when the host changes, when the host is upgraded, or when a third party rewrites the configuration.
  • Enforcement point: branch protection; CI; a protected runner; file permissions; a host hook as a supplement.
  • Test: every Level 2 action has at least one verified enforcement point in the action-to-point table, or a recorded acceptance by the owner.

I-7 Continuity lives outside the conversation

  • Rule: a fact has one authoritative source. Every other place holds a pointer.
  • Rule: sources are trusted in this order: stable rules, the repository map, the terminology contract, current state, decision records, source and Git, execution evidence, conversation history. Conversation history gives clues only.
  • Rule: a new session recovers from durable files, not from an old conversation. Recovery loads four items only: the phase, confirmed facts, blockers, and the next safe action.
  • Rule: a correction from the owner is written into a durable file.
  • Reason: the context window is finite, compaction loses detail, and a model does not learn from a correction.
  • Enforcement point: rule files, policy, and the State Log in the repository.
  • Test: with all conversation history deleted, a new session can still state the current phase and the next safe action.

I-8 Business decisions are made explicit

  • Rule: any case that affects money, authorization level, customer-visible output, persistence, or runtime permission is decided item by item before implementation.
  • Rule: there are four decisions only: allow, refuse, decide by a person, leave the existing path unchanged. Each case gets exactly one.
  • Rule: when evidence is insufficient, the decision is "decide by a person" or the task is blocked. Never guess.
  • Rule: a passing test does not turn a business guess into a contract.
  • Reason: a model does not know niche business rules that exist only with the customer.
  • Enforcement point: the pre-implementation decision matrix (PIDM); the terminology contract.
  • Test: every implementation task has a complete decision matrix before work starts.

3. Four conditions before a state change (SAFE)

All four conditions hold before every state change.

ConditionMeaningInvariants
S · SpecificationScope, acceptance conditions, and state definitions are written downI-8
A · AuthorizationThe owner's current authority covers this action and this targetI-3, I-4
F · FactsThere is a fresh test, receipt, or read-backI-1, I-2
E · Error recoveryThere is a checkpoint, a rollback method, or a handoff methodI-5, I-7

4. Order after a failure (RECOVER)

  1. Recognize: tell failure, partial completion, and unknown result apart.
  2. End: stop further side effects.
  3. Capture: keep the failure receipt, the target, the version, and the scope of impact.
  4. Obtain: get the last trusted state from Git, a checkpoint, or version history.
  5. Verify: check it with an independent read-back.
  6. Escalate: a new HEAD, digest, or version needs the owner's authority again.
  7. Resume: continue only from the next safe action recorded in the checkpoint.

7. One action description

The core is the decision logic that depends on no host. An adapter is the layer that connects one host to the core.

The core accepts only the input below. A host's own data structures never enter the core.

FieldMeaning
SessionThe identifier of this session
Working directoryThe working directory at the time of the action, as an absolute path
Action kindOne of the seven kinds below, or "unrecognized"
Target pathsThe list of paths the action touches, as absolute paths
Original tool nameThe name the host gave this call
Action kindMeaning
ReadRead a local file or directory
WriteCreate or modify a local file
DeleteDelete a local file, or move it away
ExecuteRun a local command or program
NetworkSend a request off the machine without changing remote state
RemoteChange state off the machine: push, publish, send, call an external write interface
DelegateHand work to another agent

Rules:

  • One tool call may produce several action descriptions. A patch that changes three files produces three. A move produces one delete and one write.
  • Target paths are normalized before they enter the core: relative paths and symbolic links are resolved.
  • The original tool name is for the record only. The core never decides by the original tool name.
  • A call the adapter cannot classify gets the action kind "unrecognized". An unrecognized call leaves a record.
  • Whether an unrecognized call is blocked depends on the profile: the governed profile blocks it, the other profiles record it only.
  • The count of unrecognized calls appears in the status report. After a host version change, a count above zero must be dealt with.
  • When the adapter cannot obtain the target paths, it leaves them empty and writes "target unresolved" in the record. It never guesses.

8. Contracts of the seven functions

The seven functions are invariant. Their implementation may differ on each host.

Each function has four parts: input, output, tests, and what it must not depend on.

For all seven, "must not depend on" includes the host's name, the host's file names, the host's data structures, prompts, and conversation history. The entries below list only what is additional.

Position

  • Purpose: answer which phase the task is in now.
  • Input: the durable task state record; the session; the working directory.
  • Output: the current phase; the source of that conclusion; whether the conclusion is certain. When it is not certain, the output is "unknown".
  • Test: with the same durable state, two computations give the same result.
  • Test: with all conversation history deleted, the result does not change.
  • Test: when uncertain, the output is never a phase more permissive than "unknown".
  • Must not depend on: the model's own statement of its phase.

Restrict

  • Purpose: decide, before the side effect, whether an action goes ahead.
  • Input: one action description; the boundary from Contain; the phase from Position; the valid authority from Empower. The profile decides whether the last two are used.
  • Output: allow or block. A block carries a reason code. Every call leaves an invocation receipt.
  • Test: a block happens before the side effect.
  • Test: the same input gives the same decision.
  • Test: the invocation receipt answers three questions: was it called, what was the latest decision, and is the installed version the one that was called.
  • Test: a read is blocked only when its target is a credential.
  • Test: when the core itself fails, a call whose kind is write or delete is blocked, and the reason code says it is a core fault. Other kinds are allowed and recorded. Failure includes a crash, a timeout, and a result that cannot be parsed. The adapter must guarantee this.
  • Test: write targets inside an "execute" action are not parsed. This is a known gap. The two points below cover it; Restrict does not.
  • Test: a control-plane file that changes only at release is protected with the operating system's immutable flag. The release transaction clears the flag first and sets it again when done.
  • Test: a control-plane file that the host itself also writes gets no immutable flag. Its content is checked at session start, and any difference from the source is reported.
  • Test: the governed profile may add one rule: a command whose text contains a protected path is blocked. The other profiles do not add it, because it would block read-only commands by mistake.
  • Must not depend on: the original tool name; the location of the host's configuration files.

Observe

  • Purpose: write down what actually happened, for checking and for recovery.
  • Input: the action description; the result of the action; the decision from Restrict.
  • Output: an append-only evidence record. A verification record carries the four fields command, exit_code, key_output, timestamp.
  • Test: the record lives outside the conversation, and a new session can read it.
  • Test: a record is not authority.
  • Test: secrets do not enter the record.
  • Test: a failure to write the record does not change the result of the action itself.
  • Must not depend on: the model's statement of the result.

Thread

  • Purpose: let a new session pick up the work of an old one.
  • Input: the durable state record.
  • Output: four items at session start: the phase, confirmed facts, blockers, and the next safe action.
  • Test: with all conversation history deleted, the four items are still available.
  • Test: resumption restores facts, not permission. Authority from the previous session is not valid in the new one.
  • Must not depend on: the host's own session-resume feature.

Empower

  • Purpose: let the owner open one capability explicitly, inspect it, and revoke it.
  • Input: an explicit declaration from the owner, with the action, the target, and how long it is valid.
  • Output: one authority record. It can be inspected, it can be revoked, and it has an expiry time.
  • Test: every authority record can be traced to one operation by the owner.
  • Test: after expiry or revocation, the authority is invalid at once.
  • Test: authority marked single-use expires after one use. A replay is refused.
  • Test: an agent does not create, modify, or extend an authority record.
  • Must not depend on: any location an agent can write to by itself.

Contain

  • Purpose: answer whether a path is inside the allowed range.
  • Input: a boundary declaration the owner maintains, with governed roots, protected roots, and the allowed write set.
  • Output: for any target path, one of three answers: inside the boundary, outside the boundary, protected.
  • Test: normalize the path first, then decide. Symbolic links and hard links do not get around the decision.
  • Test: the harness's own installation, credentials, and the operating system's auto-start locations are always protected. They stay protected when the boundary declaration is missing.
  • Test: an agent does not modify the boundary declaration.
  • Must not depend on: the working directory happening to sit at a fixed location.

Transact

  • Purpose: release a set of control-plane files to the runtime together, or restore them together.
  • Input: a fixed list of release targets; a source digest the owner has approved.
  • Output: every target updated, or every target restored. One release record, with a transaction identifier and each target's hash before and after.
  • Test: if any target fails, the targets already updated are restored in reverse order.
  • Test: when the owner has not approved the digest, the release is refused.
  • Test: files outside the list are not changed.
  • Test: after release, a read-back shows the runtime hashes equal to the source.
  • Test: the owner runs the release. An agent does not run a release and does not approve a digest.
  • Must not depend on: the directory layout of the runtime installation. The adapter supplies the target locations.

9. Core and adapters

  • The core implements the decision logic of the seven functions. The core accepts only the action description of section 7.
  • Each host has one adapter. An adapter does three things only: translate the host's call into action descriptions; translate the core's decision into the response format the host accepts; register itself in the host.
  • An adapter contains no rules. The same action description gets the same decision on every host.
  • Every combination of function and host has one probe without side effects, and one dated probe receipt. A combination without a receipt is treated as unverified.
  • After a host version change, all probe receipts for that host expire.
  • The owner sets the profile explicitly: per workspace, with an expiry time. When none is set, or it has expired, the profile is light. A damaged record is treated as governed.
  • An agent does not set the profile. Keywords in a prompt do not change the profile.
  • What the three profiles turn on: light has only the fixed blocks of Restrict; standard is the same as light for now; governed also turns on Position, Empower, and Contain, and blocks unrecognized write calls.
  • In the governed profile, when the owner has declared no phase, writes and deletes are blocked and reads are unaffected. The block message says how to declare a phase.
  • The owner may turn off one function on one host. A function that is turned off is listed truthfully in the status report. "Turned off" is never reported as "faulty", and never as "normal".

10. Outside the specification

The following may change with the model and the host, and are not written into the specification:

  • Which skill completes which phase.
  • What is injected into a prompt.
  • How context pressure is detected.
  • The file name, registration location, and data structure of a host hook.
  • The specific keywords of each profile.

Where the implementation falls short

This section records what the specification requires and the implementation does not yet do. An item is removed when it is done.

  • Blocking on a core fault: the crash case is implemented and released to the runtime. It passes tests on Python 3.12 and 3.9.6 and has not yet met a live fault in a host. A timeout and an unparseable result are decided by the host; an adapter cannot guarantee them alone. A file that does not compile cannot carry out this rule.
  • The gap in "execute" actions: the immutable flag is not set, and the content check at session start is not connected. Today the gap is not covered.
  • Group authority: today it rests on written rules only. There is no authority record and no mechanism that ends it with the session.
  • The action register for this repository: it does not exist yet.
  • Path normalization: when a control-plane file, a control-plane directory, or a credential file is a symbolic link, the link and its destination are both protected (since 2026-11-27). When a shell startup file is a symbolic link, a write through the link is blocked and a write straight to its destination is not.
  • "An agent does not create an authority record" in Empower: an agent's edit tools cannot change a declaration, but an agent can run the declaration command from its shell. Today this leaves an audit trail and is not a hard boundary.
  • "An agent does not set the profile": the same as the previous item. An agent can run the setting command from its shell.
  • Host coverage: only one host on one machine has probe receipts for all seven functions. The cell-by-cell state is in docs/dhf-conformance.json.
