Evolution Evidence · CAP / BRIDGE

From business blockage to governed enforcement.

DHF did not begin as an acronym system. It developed as ShipQ exposed recurring continuity, accuracy, and permission problems. Each stage below pairs a customer problem with a control change and the evidence needed to claim progress.

B · Baseline

Recover position

Value problem

Interrupted sessions lose ownership, state, and a safe next action.

Evidence required

Durable state, clean ownership, and a recovery output that does not invent permission.

R · Routing

Route by lifecycle

Value problem

Planning, implementation, validation, and handoff actions blur together.

Evidence required

Phase-specific routing and tests proving forbidden transitions are blocked.

I · Integration

Bind project truth

Value problem

Generic agents miss repository vocabulary, business correctness, and source ownership.

Evidence required

Repo adapters, contracts, and source-linked verification for domain decisions.

D · Delivery

Make completion checkable

Value problem

Agents claim completion without a current artifact or readback.

Evidence required

Fresh command, exit code, key output, timestamp, and artifact readback.

G · Governance

Match control to risk

Value problem

Low-risk edits and production mutations receive the same handling.

Evidence required

Risk profiles, authorization records, and fail-closed denial tests.

E · Enforcement

Protect runtime change

Value problem

Documented rules can still be bypassed during promotion or external execution.

Evidence required

Protected runtime controls, atomic promotion, exact parity, and production readback.

Evidence boundary: an evolution stage describes a capability target. Current source, runtime, publication, and production status must still be verified separately.
