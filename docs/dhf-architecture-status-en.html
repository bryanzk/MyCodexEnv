DHF architecture and current status.

This page is the canonical public snapshot for MyCodexEnv and Delivery Harness Framework. It separates repository source, one machine's active runtime, published documentation, and the proposed independent DHF core. Source available is not runtime active.

Four statuses, never one vague “done”

Repository source: implemented

The audited local main contains a host-neutral Guard core with adapters for Codex and Claude Code, the lifecycle router, hooks, evidence schemas, recovery, checkpoint, ledger, transition store, compaction observation, session bearing, context meter, the host conformance table, and tier-1/2 behavior evals.

Local runtime parity: verified 2026-08-10

The full comparison, 24/24 managed files matching source, was last run on 2026-08-10 and has not been repeated since. What is newer is narrower: on 2026-11-27 a reversible seven-target promotion ran on one machine, the seven promoted files match the source, and Codex CLI 0.155.1 passed a side-effect-free probe for each of the seven functions. These are local receipts, not production rollout.

Public pages: rewritten 2026-11-27 from the conformance table

From 2026-08-18 to 2026-11-26 these pages described a Guard that was failing on every call on the reference machine. The governance, PROTECT, and status pages now state what each host enforces and what has a passing probe. The date is when the source was rewritten; a page is current only after GitHub Pages has built it.

Independent DHF core: not published

The Guard's decision logic is host-neutral and lives in dhf/core of this repository, with one adapter per host. It is not a separate product: no independent repository, immutable release, tag, or upstream pin is asserted. MyCodexEnv remains the working source and consumer boundary.

Current architecture

1 · Host and runtime hooksSessionStart: naming → session_bearing.py. UserPromptSubmit: compaction_probe.py → dhf_preprompt.py, which the owner has turned off on the reference machine. PreToolUse: harness_guard.py. PostToolUse: harness_observer.py. On Claude Code the Guard is one PreToolUse hook installed in the repository.
2 · Generic router and repo adaptersThe generic dispatcher honors opt-out first, lazily delegates known repositories, and otherwise routes explicit DHF work by lifecycle stage. Project paths, fixtures, commands, and business boundaries stay in repo-specific adapters.
3 · Lifecycle and specialist workflowsEight normalized stages—research, requirements, planning, development, validation, review, ship, handoff—select planning, TDD, QA, security, release, documentation, or deterministic helpers.
4 · Durable governance and evidenceharness_recover.py, harness_checkpoint.py, harness_ledger.py, harness_transition.py, harness_eval.py, schemas, state logs, and fresh four-field verification receipts make work recoverable and auditable.
5 · Distribution boundarycodex/ is repository source. ~/.codex is machine runtime. Promotion is explicit, targeted, reversible, and needs the owner to approve the source digest first. The Claude Code adapter travels with a repository instead. Public docs and any future independent-core release are separate publication lanes.

Verification boundary

Principle: a historical green result is never reused as proof of the current runtime. After any deployment or environment change, DHF re-runs its source tests, file-by-file parity checks, and environment verification before claiming completion.

Every completion claim is backed by a fresh, machine-checkable verification receipt rather than by memory or past status.
