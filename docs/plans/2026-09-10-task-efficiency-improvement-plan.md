### A1：全局人工接手与拒绝处理

未来源码 write set：`MyCodexEnv/codex/AGENTS.md`。拟增加两条短规则：

> 当当前授权内的直接工具可以快速完成时直接执行。若操作已明确、用户通常可在一分钟内完成，并且已确认工具无支持入口、受到明确限制，或适用 skill 的既有重试与时限预算已耗尽，给出准确页面、目标、已准备文件和一步操作；保留当前状态，并继续不依赖该步骤的已授权工作。适用 skill 的预算耗尽后，不以更换 locator 或重开页面重置尝试次数。

> 同一审批拒绝在授权、证据或外部状态未变化时，不重复申请或改写命令尝试。外部写入结果不确定时先只读确认；发布、发送、创建等操作未确认结果前不得重发。新的用户输入、诊断证据或状态变化仅允许重新评估受影响步骤，不扩大授权。

这些是执行选择，不是工具强制取消机制。需要用户操作时只询问实际缺失动作，不重新申请已拥有的授权；用户未回复不构成批准。没有窄 skill 时，在当前工具支持的时限内继续等待，观察到实际失败后再诊断，不发明额外预算器。普通 UI 调用期限服从当前工具支持和相关 skill，图片生成、构建和必要长测不套用一分钟限制。

验收：一个无直接入口的短 UI 操作、一个可直接完成的 API 操作、一次相同审批拒绝、一次结果未知的发布，分别走人工接手、直接执行、停止无效重试、只读确认。反例：工具仅稍慢且仍在支持时限内时继续等待，不要求用户操作。不能把用户手动接手当作自动化成功。

## 6. 源码、runtime 与恢复顺序

1. **源码批次**：实施前记录实际 root/branch/HEAD、准确写集和用户 dirty 基线；只修改 A1、A2 已批准文件。MCE 源码按当前 scoped gate 和最终仓库 gate；ShipQ 纯指令改动按自身例外。两个 repo 分别验证，不把其中一个测试当另一仓库证明。
2. **定向 promotion**：只有 A1 源码通过且用户批准准确源／目标摘要后，考虑 `MyCodexEnv/codex/AGENTS.md` → `/Users/kezheng/.codex/AGENTS.md`，是否创建缺失目标必须明确。按现有 promotion skill 备份、copy、cmp/hash、非目标比较及前后门禁执行；禁止运行 broad sync。项目局部 A2 不复制到全局。
3. **automation 批次**：按 B1→B2 优先，随后处理确有差异的项；每次 mutation 都核对当前对象与获准快照。各 ID 的回读不能替代首次实际执行证据。
4. **恢复**：源码问题仅撤销本轮已证明归属的变更；runtime 按已验证目标备份恢复；automation 用原配置快照通过同一工具恢复该 ID。先核对当前状态，遇到用户／并发修改先停，不覆盖。恢复范围必须包含在实施授权中，无法安全恢复则报告具体状态，不删除备份。

源码改了不代表 runtime 已加载；磁盘 parity 也不证明执行行为。未来获准推广时分别报告 `source_implementation`、`runtime_parity`、`runtime_activity`；后者没有宿主证据就写 `not_proven`。本轮只交付计划，不运行上述实现／promotion gate。

## 7. 验收与是否继续

本轮计划评审只要求可追溯、边界清楚、当前能力与待实施项分开、步骤可执行且不新增无依据机制。对四个场景作语义复核：上传卡住、配置被拒、展示标题修改、已实现但 Todo；并检查相反案例：必要长测不被强制中断、发布结果未知不重发、价格／单位变更不走展示例外、运行验收缺失不能由已提交代码代替。

文档验证只做引用可定位、准确 write set、空白／Markdown 基础检查；绝不把关键词存在视为行为正确。运行在 MCE 根目录的 `git diff --check -- <两个计划文件>` 不覆盖 untracked 文件，因此还需直接读取检查新文件。开始时工作区 clean；以后有用户改动时比较起点而非要求整个工作区 clean。

未来实施后的效果，只在当前自然发生的任务遇到相关场景时，复用该任务日志判断有无具体重复，必要时在原交付中说明一句。可读取的指标为回合时间、模型请求、未缓存输入和重复工具调用；工具等待与用户等待应分开，无法拆分就标明。没有同类场景或缺少 usage 时写效果未验证，不追加采样任务、不做跨线程跟踪、不新增固定报表。

停止标准：当前批次要求的改动和有效验证已完成就交付；没有新增信息不重复 gate、浏览器预览或评审。发现现行能力已经覆盖则 NO-OP。发现与本次改动直接相关的失败，只修复获准范围；需要插件能力修复、权限变化、跨任务存储或扩大 gate 范围时暂停该部分并另列最小决策。

## 8. 已知未知与残余风险

- 现有发布 skill 已经写出恢复规则；历史故障可能早于当前规则，也可能是执行未遵循。本文不推定规则生效时间或根因已经解决。
- UI 工具可能忽略期限或失去连接，规则无法保证硬取消；不能通过无授权的控制路径绕过。
- 长 heartbeat 历史的首轮输入不会因缩短 prompt 自动消失。本计划不改上下文管理配置，不自动新建／迁移／归档任务，也不承诺 token 降幅。
- 人工接手耗时是估计，用户不在场时可能更慢；先选择当前授权内已有的快速直接入口。
- 展示例外依赖准确的 diff 分类；混入业务行为或合同变化时保留原 gate，不能为省时扩大定义。
- 当前可见规则可能变化；未来实施先读当前权威入口。评审通过证明的是此范围内计划的完整性，不是线上发布、runtime 生效或生产效率提升。
